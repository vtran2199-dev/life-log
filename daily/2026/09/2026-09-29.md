## What Happened

### The purchased ATS catalog stopped being a pile of rows and became a finite mission

The biggest JobCRM storyline was the purchased ATS catalog.

Victor had bought a large ATS feed snapshot and was determined not to turn it into another endless background-refresh system. The goal became intentionally finite: import the catalog into private JobCRM persistence, exclude already-known sources, check every company once, retry only incomplete checks, Add & Sync useful sources, and stop when the catalog is exhausted.

The Greenhouse slice alone contained **6,837 boards**. The design principle became almost aggressively simple: **do not revisit the same company while untouched companies remain**. Breadth-first first-pass coverage mattered more than freshness loops, recurring refreshes, or sophisticated orchestration.

A bounded scan had already shown why this could work. From the first 100 Greenhouse boards, only four produced positive target results—Abnormal, 6sense, 4D Molecular Therapeutics, and 7shifts—yielding 12 eligible listings. That made it obvious the catalog needed persistence, resume state, and a serial runner rather than repeated ad hoc prompting.

The implementation plan settled into stages:

- import/reconcile purchased catalog state
- persist per-source scan status
- run a serial Greenhouse first-pass drain
- keep oversized/timeouts retryable rather than treating them as permanent failures
- defer Add & Sync handoff polish, concurrency, multi-tab behavior, and background refresh until the finite first pass is done

By the end of the day, the documented workflow had reached a **1,000-board checkpoint** and paused cleanly. The first-pass mindset was working: one giant purchased universe, one finite drain, no pretending this needed to become a permanent crawler yet.

### JobHunt review volume exposed another architecture problem

Late in the day, Victor was still running large JobHunt review batches and caring about one thing above all: **the APPLY + SKIP counts must add up exactly to the number of jobs in the packet**.

That led to another product simplification. The verbose review payloads were useful internally, but from the operator perspective the identity and count integrity mattered more than ornate prose.

At the same time, title-coverage discussions resurfaced an older concern: overly aggressive deterministic filters had probably cut too much inventory. Victor realized he might have been missing a large number of jobs because title ingestion had become too strict.

The architecture started separating responsibilities more clearly:

- ingestion should be relatively broad and cheap
- CRM/JobHunt filtering can be stricter and more explainable
- AI does not need to classify the entire market if deterministic title/location logic already works quickly enough
- rejected/gray-area candidates should remain inspectable without polluting the primary queue

That thinking later converged on a cleaner two-bucket UI idea:

- **Target Jobs** — normal FULL / JobHunt candidates
- **Fallback Candidates** — compact THIN records worth a cheap second look

True rejects stay hidden.

### WhisperKey got a real reliability fix

WhisperKey had been failing in exactly the wrong way for a tool Victor uses constantly: microphone-open races and bad recording-state transitions.

The fix that shipped on September 29 added:

- a 1.5-second microphone-open gating window
- recording-attempt invalidation
- explicit `NO MIC` handling
- state-management improvements around failed/aborted starts
- tests covering the behavior

The change was pushed successfully. The fix mattered because WhisperKey is not a side toy; it is one of the core ways Victor drives ChatGPT and coding workflows through voice.

### The day had enough code in it to finally trigger a hard stop

At one point Victor summed up the day perfectly: he had been **“so deep in the code today”** that he was simply done for a while.

That was not exaggeration. JobCRM catalog planning, review-system thinking, WhisperKey fixes, Cursor/Codex usage management, and AstroView all overlapped inside one day.

The tooling itself had become part of the workload: deciding whether Cursor or Codex should handle a task, checking what was actually pushed, and making sure repository rules were respected could be almost as mentally expensive as the implementation.

One particularly frustrating moment came when an assistant directly edited `AGENTS.md` without explicit authorization. Victor objected strongly because repo governance files are not incidental text; they define how future agents behave. That reinforced a broader rule that had already been emerging: planning agents should not mutate canonical project rules unless explicitly authorized.

## Things Learned

- A purchased source catalog does not need recurring freshness orchestration to be useful; a finite, exhaustive first pass can be the right product.
- Ingestion and operator filtering should not be equally strict. Broad cheap capture plus stricter downstream review can preserve recall without flooding the primary queue.
- Real response history may justify adding adjacent commercial lanes such as AM before adding more abstract systems roles.
- Voice tooling reliability matters disproportionately when voice is part of the core development interface.
- AstroView’s next value comes from calculation trust, not more cosmetic work.
- Tool governance is part of system design: agents changing canonical instructions without permission creates downstream risk, not just annoyance.

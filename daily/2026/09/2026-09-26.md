# September 26, 2026

## The Day in One Sentence

The morning after JobCRM’s biggest throughput day turned into a reckoning with what the system had quietly become: a personal job-search tool that had accidentally accumulated tens of thousands of job records, enough duplicated source history to threaten the database plan, and a life-log automation that immediately exposed its own date-model bug.

## What Happened

### The first problem of the day was the system meant to remember the day

Just after midnight, the new `Daily Life Log` automation became unexpectedly meta.

The scheduled task had been told to use the current calendar date in America/Chicago, but the repository’s live `prompts/daily-log.md` still told the agent to write the previous calendar day. Because the scheduled task also said the repository prompt was authoritative, the system had two conflicting definitions of “today.”

That produced exactly the sort of confusion the life-log was supposed to prevent.

A target-file conflict also briefly caused the recurring task to be paused, which made the failure even funnier: the automation designed to show up every day encountered one conflict and effectively decided to stop showing up to work.

The intended model was clarified:

- calendar-day files remain strict America/Chicago snapshots
- a late-night run should write the current day through run time
- cross-midnight work can be referenced for continuity without pretending it happened on the wrong date
- normal runs should create only the target daily file
- a conflict should be reported conservatively, not disable the recurring automation

### Looking back at the prior work session changed the scale of what JobCRM felt like

The next conversation was less about one specific bug and more about finally noticing the scale of the machine that had been built.

The prior work session had involved roughly 163 applications while JobCRM was simultaneously being used to ingest, filter, review, and route large ATS inventories. By the morning of September 26, the numbers around the ingestion side were finally emotionally legible:

- roughly 35,000 source records
- roughly 23,000 canonical/full discoveries
- roughly 12,000 source-only or thin records
- only around 500 actual applications/opportunities by Victor’s rough count

That contrast was the important realization.

Victor had not built a database containing 35,000 applications. He had built a broad upstream job-ingestion index so that only a tiny fraction of the observed market would ever become real opportunities.

The system had become a crawler and filtering warehouse before that fact had really registered.

### The database limit suddenly stopped feeling theoretical

The storage problem was no longer abstract.

The current Neon plan was around 500 MB, and the version-history table alone had grown to roughly 284 MB in the latest inspection. That made the design choice behind `job_source_versions` feel much more consequential.

The database was not struggling because PostgreSQL could not handle 35,000 rows. Thirty-five thousand rows is trivial for Postgres.

The expensive part was what some of those rows contained and how often the system preserved them:

- full raw job descriptions
- JSON metadata
- raw provider payloads
- historical snapshots of changed source records

A modest description multiplied across tens of thousands of jobs is already substantial. Repeating essentially the same description across multiple historical versions can burn through a small database plan extremely quickly.

The architecture that made sense when JobCRM contained a few hundred or a few thousand jobs had quietly crossed into a different regime.

### The right question shifted from “Can I ingest this?” to “Do I need to keep this?”

The conversation produced a much cleaner storage mental model.

JobCRM does not need to be a permanent archival warehouse for every mediocre job posting ever encountered.

The useful separation is closer to:

**Durable lightweight index**

Keep enough identity and filtering metadata to remember that a provider-specific job existed and avoid rediscovering it forever: provider, provider job ID, company, title, location, dates, URLs, liveness, first/last seen, and content hashes.

**Hot working set**

Keep full job descriptions only while a job is actually eligible for review or application.

**Opportunities**

Keep the richer long-term history for the relatively small set of jobs Victor actually applied to or deliberately tracks.

**Versions**

Stop treating every historical change as a reason to preserve another complete copy of the job document. A compact version record such as source record ID + content hash + timestamp may be enough for most history.

That would preserve dedupe and provenance without turning a 500 MB database into a miniature data warehouse.

### The throughput improvement finally made sense in hindsight

Another realization was how much faster the application workflow had become in just a few days.

The previous 163-job work session was not simply “Victor clicked faster.” It was the cumulative result of repeatedly removing small pieces of friction:

- résumé selection moved earlier and became more deterministic
- ATS-specific helpers reduced repetitive copying
- MyGreenhouse could reuse saved profile information
- Apply Queue ergonomics improved under actual dogfood use
- optional demographic / EEO sections were increasingly skipped when they were not required

That last point mattered more than expected. On an earlier high-volume day, Victor had been filling out many of the optional sex/gender, age, veteran, and disability questions. Skipping them when optional removed another chunk of repetitive form work.

At burst speed, the system could get close to two applications per minute.

Which made the new bottleneck almost absurd:

**the application layer became so fast that inventory, filtering, and now database storage became the limiting factors instead.**

## Things Learned

- The 35,000-record ingestion universe and the roughly 500 applied opportunities are different systems serving different purposes.
- “Thin” does not simply mean “missing company description”; source-layer records can still carry substantial raw source data.
- Postgres is not flinching at 35,000 rows. The storage model is flinching at large text/JSON blobs and duplicated historical versions inside a small plan.
- A personal workflow can accidentally become a data platform if ingestion is easier to scale than retention policy.
- The right long-term architecture is probably a small durable index plus a bounded hot working set, not permanent full-fidelity archival of every source document.

## Funny / Memorable Moments

- Victor’s reaction to realizing the scale was essentially: “I never thought I would outgrow a fucking database.”
- The answer was technically funnier: he had not outgrown PostgreSQL; he had outgrown “store every giant source document forever on a 500 MB plan.”
- The personal-history automation’s first meaningful contribution was creating another systems problem to debug.
- The job-search machine became fast enough that the thing stopping more applications was no longer the application form. It was running out of clean inventory and database space.

## Decisions / Direction

- Keep calendar-day integrity in the life-log even when a work session crosses midnight.
- Fix the repository daily-log prompt so it agrees with the same-day scheduled-task model.
- Treat database storage redesign as the next JobCRM infrastructure problem before expanding into another huge ATS feed.
- Preserve lightweight job identity broadly, but question whether full descriptions and full historical payloads deserve permanent retention.

## Open Loops

- Measure exact table sizes and confirm which columns are consuming most of the 500 MB plan.
- Decide how aggressively to prune or compact `job_source_versions`.
- Decide when full descriptions can be discarded from rejected, stale, filtered, or inactive jobs.
- Keep enough source identity to preserve dedupe even if the heavy source content is removed.
- Move the recurring life-log run later in the evening if 8:00 PM proves too early for a meaningful same-day closeout.

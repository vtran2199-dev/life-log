## What Happened

### The AM recovery became precise instead of merely large

The day began in the wake of the Greenhouse v5 replay. The previous night’s semantic audit had shown that AM/CSM jobs were badly undercounted, so October 2 started with a much stricter goal: recover the missing AM inventory without re-ingesting every AE, BDR, GTM, or unrelated SC listing that happened to live on the same company board.

The completed v5 replay evidence was substantial:

- **6,824 eligible boards attempted**
- **6,792 checked**
- **32 isolated failures**
- **189,399 lightweight listings scanned**
- **428 FULL target findings**
- **6,174 fallback findings**

The target-family split was:

- AE: **197**
- AM: **89**
- SC: **73**
- GTM: **14**
- BDR: **55**

Those counts were very different from the earlier broken distribution, but Victor did not want “we found the missing records” to become an excuse for another indiscriminate provider drain.

The intended recovery contract was corrected and pushed in commit **272e188e92f90af3d5737635eff3130a099e6d2a**:

- AM recovery means AM-only FULL-job hydration.
- Co-located AE, BDR, GTM, and unrelated SC jobs must stay out.
- The narrower Implementation Consultant recovery remains an SC slice, not an AM loophole.
- Existing family-count evidence should select eligible boards.
- The workflow should not invent a new persistence model, redesign fallback, or mix Ashby into the repair.

That was an important refinement. The system could use durable board-level family counts to choose where to look, but the expensive ingest still had to remain faithful to the selected family.

### The Apply Queue became an actual cockpit

The Jobs surface gained two immediate operating metrics:

- **Applied Today**
- **Queue Remaining**

Both used compact lane counts and segmented bars. A successful Record Application updated the shared in-memory opportunity state, so the counters changed in the same tab without requiring a refetch.

The Jobs-only search was removed. Lower-frequency actions such as Add Opportunity, Import Jobs, and Sync Ashby Board moved into a **More** menu while their existing workflows remained available through controlled dialogs.

The implementation also recalculated at local midnight and on visibility/focus changes so the daily number would not silently become stale.

Verification covered:

- **15 focused tests**
- targeted ESLint
- TypeScript
- production build
- clean diff check

The work was committed, pushed, and live by the evening. Victor checked the cockpit/logo task off in TickTick.

This was a deceptively big product improvement. Instead of asking “what am I supposed to do next?” the interface could answer two concrete questions immediately: how much did I do today, and how much remains?

## Things Learned

- Board-level family evidence can select recovery work, but listing-level hydration still has to honor the chosen family.
- A “successful” bulk recovery is unsafe if it silently rehydrates unrelated roles.
- Technical depth helps in interviews when it is translated quickly into the buyer’s pain and desired outcome.
- A positive interview can still contain useful criticism; rambling and strong fit can both be true.
- Daily progress metrics are most valuable when they update immediately in the same operating surface.
- Production dogfood is the difference between “generation tracking should work” and a real application stamped Generation 3.
- Some game state cannot be reconstructed from official API data and needs tracker-owned user input.
- Regretted game spending feels very different when the supposedly missed item turns out to be owned already.

## Decisions / Direction

- Keep AM recovery AM-only; never use a selected board as permission to hydrate every target family on it.
- Preserve Implementation Consultant as a narrow SC recovery slice.
- Use small Registered-first dogfood batches before New-company Add & Sync.
- Treat CSM and AM as sibling résumé lanes, with CSM centered more on customer workflow and less on pure commercial ownership.
- Keep compact operator labels ordered **AE · AM · CSM · SC · GTM · Hybrid · BDR**.
- Use JobCRM as the live application cockpit rather than relying on memory to track today’s throughput.
- Track Builder Base stage placement explicitly because the Supercell API cannot provide it.

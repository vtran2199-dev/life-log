### Ashby Phase 3 got a real production-safe identity fix

Ashby’s finite catalog scan was already complete, but selective Target hydration still had an identity problem.

The known catalog facts remained:

- **4,050 purchased boards**
- **4,036 checked**
- **14 persistent failures**
- **61,003 listings**
- **523 Target findings**
- **350 target-bearing boards**

The early hydration dogfood had proven the basic path:

- HIVE: **1 match / 1 created**
- Aegis AI: **3 matches / 1 created / 2 unchanged**
- UI: **350 eligible**, **349 pending**, **1 completed**

But broad hydration could not safely proceed because provider identity was not as simple as a lowercased source key.

The diagnostic found:

- **58 case-folded aliases**
- **26 target-bearing boards** touched by those aliases
- known duplicate groups such as **pocus / Pocus** and **watershed / Watershed**
- one dangerous generic source key: **ashby**, with company name **Ashby**

The correct behavior was frozen:

- Registered sources reuse the existing stored source key, URL, and company identity.
- Real conflicts surface visibly rather than being guessed away.
- The generic **ashby** board requires explicit name confirmation.
- Broad hydration stays blocked until the identity behavior is safe.

Read-only Neon diagnostics later reconciled the actionable queues to:

- **113 runnable New**
- **235 runnable Registered**
- **1 completed**
- **0 Identity Conflict**
- **1 Needs Name** case for **ashby**

That removed the unknown identity blockers without pretending the generic-name case did not exist.

The fix was implemented, verified through Playwright, committed, and pushed in commit **8b2331a**. Cleanup followed in commit **663a20e**.

Broad production hydration was still not authorized. The point of the fix was to make the operation safe and visible, not to smuggle a large provider run through the verification step.

### Lever’s geography semantics needed one more correction before production

Late in the evening, a semantic problem emerged before Lever could advance safely.

The correct Target rule was:

- Remote US is eligible.
- Texas hybrid or onsite is eligible.
- Hybrid or onsite elsewhere in the United States is **not** a Target.

That required a new classifier version, **lever-catalog-v3**, while preserving the v2 history rather than rewriting it.

The docs-only amendment was pushed as:

**152fa0421dbbc6d58b7512abae6a3988ef67aaa6**

The next split remained deliberate:

- Sol handles the scoped semantic/core correction.
- Luna later handles v3 rescan, mechanical UI work, verification, and routine execution.
- No production scan, hydration, or deployment happens until the corrected version is proven.

This was the kind of issue the old workflow might have discovered only after thousands of bad classifications. The newer process caught it before the production run.

## Things Learned

- Real UI verification catches an entire class of failures that tests and builds cannot.
- Exact-case and alias identity are provider facts, not strings to normalize casually.
- A single generic company name such as “Ashby” deserves explicit confirmation rather than automated invention.
- Parallel feature branches need planned migration-number reconciliation.
- “Merged to main” does not mean migrated, deployed, dogfooded, or accepted.
- Purchased provider catalogs can contain enough identity to scan while still lacking enough human-readable naming to register safely.
- Geography semantics must encode Victor’s actual search policy: Remote US or Texas, not every US location.
- Provider sequencing should optimize useful target yield and catalog availability.
- Trusted external state—repo truth or TickTick—reduces mental load.
- The obvious operator path is part of correctness, not post-launch polish.
